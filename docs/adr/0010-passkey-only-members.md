# パスキーのみの会員を認め、復旧は管理者リセットで認証情報を全初期化する

## ステータス

採用

## 決定

- 会員の認証情報は「パスワード(0〜1)」と「パスキー(0〜n)」。**常にどちらか1つ以上**を持つことをサーバーで強制し、最後の1つを消す操作は拒否する。
- 「パスワード認証の無効化」はフラグではなく**パスワードの削除**とする。再び使うときは新しいパスワードを設定する。
- 会員登録(ブートストラップを含む)はパスワードとパスキーのどちらでもできる。パスキーでの登録も、パスワードでの登録と同じ世帯の作成・招待による参加を伴う。
- パスキーのログインはユーザー名を入力しない方式(discoverable credential)とする。
- 認証情報の追加・削除には、既存の認証情報(現パスワードかパスキー)による直近5分以内の本人確認を要する。ログイン直後は本人確認済みとみなす。削除系の操作では、操作した端末以外のセッションを破棄する。
- アカウント削除と super_admin による他ユーザー削除は、操作者のパスワードを送ればそれで確認し、送らなければ直近の本人確認を求める。パスワードのない会員・super_admin も操作できる。
- 端末を失くした会員は、**管理者のパスワードリセット**(ADR 0004)で復旧する。リセットは一時パスワードを発行して強制パスワード変更の状態にし、同じトランザクションで**全パスキーを削除**し、全セッションを破棄する。
- 強制パスワード変更中は、パスキーの操作も本人確認もできない。先にパスワードを変更する(リセットでパスキーは消えているので困らない)。
- 本人確認のパスワード経路は、ADR 0007 の認証試行制限を他の入口と共有する。パスキーの署名検証(ログイン・本人確認)は試行制限の対象外とする。

## 背景・理由

- フラグで止める方式では、再び有効にしたときに漏れたかもしれない旧パスワードが復活してしまう。削除なら「ある/ない」の2状態で済む。
- 招待制・家族規模の運用のため、メールによる復旧の仕組みは持たない。復旧窓口は既存の管理者リセットに一本化する。
- リセットが必要になるのは、端末の紛失や乗っ取りのときがほとんどである。その時点のパスキーは信用できない(盗まれた端末や攻撃者が追加したものかもしれない)ため、すべて消す。
- パスキーの署名は推測できないため、総当たりの対象にならない。

## 帰結

- 管理者がリセットすると、対象の会員はパスキーを登録し直す必要がある。
- RP ID は公開ドメインに紐づくため、ドメインを変えると全パスキーが使えなくなる。
- users を作り直すマイグレーションで関連データが消えないよう、マイグレーション適用中は外部キーを無効にし、適用後に整合性を検証する。
