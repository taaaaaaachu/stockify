# ADR 0013: たまにしか使わない品目の手動管理モード

- Status: Accepted
- Date: 2026-11-15

## Context

残量は購入・使い切り・残量補正の履歴から消費レートを推定して求めている(ADR 0001)。洗剤やトイレットペーパーのように定期的に消費する品目には合うが、電池・電球・季節物の洗剤のように「たまにしか使わない」品目では、購入間隔が消費ペースを表さない。時間経過で残量が減り続け、誤った枯渇予想・購入推奨・通知が出てしまう。

## Decision

ストック品目に**管理モード** `trackingMode: 'estimated' | 'manual'` を持たせる(既定・既存行は `estimated`)。

- **手動モード**では消費レートを推定しない。残量は「最後のアンカー(初回購入または残量補正)+ 購入 − 使用」の実数で、時間経過では減らない。
  - 新しいイベント**使用 (UsageEvent)**「これだけ使った」を購入・使い切り・残量補正と同格の子レコード(`usages` テーブル / IndexedDB `usages` ストア)として追加する。手動モードの品目にだけ記録でき、推定モードの品目への記録はエラーにする。
  - 残量ウォーク(`walkRemaining`)に減算イベント `sub` を加え、区間レートを常に 0 とする。残量は 0 未満にならない。同時刻の処理順は add → sub → set。使い切りは従来どおり 0 への set。
  - 推定結果は `remaining` だけが意味を持ち、`ratePerDay` / `depletionAt` / `recommendedPurchaseAt` は常に null。
- 手動モードは購入推奨リスト(枯渇ベース)に決して出さない。代わりに品目ごとの閾値 `lowStockThreshold`(null なら通知なし)を持ち、残量がそれ以下なら状態 `low`(**在庫わずか**)として買い物リスト画面とプッシュ通知の対象にする。購入等で閾値を上回れば外れる。
- **推定 → 手動**の切替では実際の残量 `currentRemaining` を必須とし、切替と同時にその値を現在時刻の残量補正として記録して新しいアンカーにする。推定残量はモデル値で、手動管理の起点として信用できないため引き継がない。会員のオフライン操作(ADR 0009)では、端末とサーバーで同じ補正 ID(`adjustmentId`)を使い、再送で二重記録しない。
- **手動 → 推定**の切替は履歴をそのまま使う。使用イベントは推定モードでは無視する(推定の挙動は導入前と一切変わらない)。

## Consequences

- 推定モードの品目の推定・買い物リスト・通知は変わらない。既存データは推定モード・閾値なしとして移行する(SQLite は列の既定値、ゲストの IndexedDB は v4 アップグレードで埋める。旧形式のエクスポートも推定モードとして取り込める)。
- 手動モードの品目カードは推定残量・枯渇予想・購入推奨日を出さず、「残り N」と最終確認日(最後のイベント日時)と「手動」バッジを表示する。
- 手動モードで使用の記録を怠ると残量は実態より多いまま残る。気づいたときは残量補正で直す運用とする。
- 定期便は手動モードでも購入を生成し残量に加算されるが、枯渇前の補充判定(ADR 0002)は推定しないため働かない。

## Alternatives considered

- 推定モードのまま消費レートを手入力で 0 にする: 「時間で減らない」ことはできるが、使った分を差し引く手段がなく、補正を毎回入れる必要がある。
- 使用を残量補正で代用する(使うたびに残量を入力): 差分ではなく絶対値の入力になり、「3 本使った」をそのまま記録できない。履歴から使用量も読み取れない。
- 推定 → 手動の切替で推定残量を引き継ぐ: 推定がずれている品目ほど手動へ移したくなるため、誤った起点を固定してしまう。
- 推定モードでも使用イベントを減算に使う: 推定の消費と二重に差し引くことになり、既存の推定の意味が変わる。
