# 消費推定モデル: 使用を記録せず購入履歴の長期平均から残量を推定する

## 決定

日々の使用は一切記録させない。ユーザーが記録するのは**購入(内容量+購入日時)だけ**とし、残量・枯渇予想はモデルによる**推定値**として提示する。

消費レートは**長期平均方式**で求める。すなわち「累計購入量 ÷ 初回購入からの経過時間」を基本式とし、直近1ペアの購入間隔から逆算する方式は採らない。初回購入時のみ、履歴が無いため`仮の値`(この内容量を約○日で使い切る想定)でブートストラップする。

推定のズレは任意の補正で直せる:`使い切り`(空になった)イベントと`残量補正`(今これくらい残っている)。特に使い切りイベントは、その量をその期間で消費した確定サンプルとしてレート推定の最優先シグナルにする。

## 背景・理由

- このアプリの本質は「なくなる**前に**買い足す」こと。ところが「前回の内容量 ÷ 前回から今回までの間隔」でレートを出すと、早めに買い足す人ほど間隔が実際の使い切り期間より短くなり、**消費を過大評価**する(まとめ買いでは過小評価)。購入タイミングのブレが直接バイアスになる。
- 長期平均方式なら、長期で見れば「買った総量 ÷ 経過時間 ≒ 消費レート」が成り立ち、早買い・まとめ買いのブレが平均化されて相殺される。購入を重ねるほど自己補正的に正確になる。
- 日々の使用記録を求める設計は、正確だが続かない(習慣として破綻しやすい)。記録の負担を「買ったときだけ」に絞ることで継続性を優先し、精度は長期平均と任意補正で担保する。

## 帰結

- 残量は常に推定値であり、ユーザーには「推定」であることが伝わる表示にする。実測が要るユーザーは使い切り/残量補正で原点を直せる。
- 購入が1回だけの品目は仮の値に依存し精度が低い。回を重ねて改善する前提を UI でも示す。
- 消費レート・残量・枯渇予想日・購入推奨日の算出は副作用のない純粋関数(`src/lib/domain`)に置き、単体テストで固定する。
- 「同じ品目でも回によって内容量が異なる」を許すため、レートは内容量固定を仮定せず購入ごとの実内容量を積算する。
