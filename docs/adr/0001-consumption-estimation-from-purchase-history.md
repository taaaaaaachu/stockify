# 消費推定モデル: 使用を記録せず購入履歴の長期平均から残量を推定する

## 決定

日々の使用は一切記録させない。ユーザーが記録するのは**購入(内容量+購入日時)だけ**とし、残量・枯渇予想はモデルによる**推定値**として提示する。

消費レートは**長期平均方式**で求める。すなわち「累計購入量 ÷ 初回購入からの経過時間」を基本式とし、直近1ペアの購入間隔から逆算する方式は採らない。初回購入時のみ、履歴が無いため`仮の値`(この内容量を約○日で使い切る想定)でブートストラップする。

推定のズレは任意の補正で直せる:`使い切り`(空になった)イベントと`残量補正`(今これくらい残っている)。特に使い切りイベントは、その量をその期間で消費した確定サンプルとしてレート推定の最優先シグナルにする。

## 背景・理由

- このアプリの本質は「なくなる**前に**買い足す」こと。ところが「前回の内容量 ÷ 前回から今回までの間隔」でレートを出すと、早めに買い足す人ほど間隔が実際の使い切り期間より短くなり、**消費を過大評価**する(まとめ買いでは過小評価)。購入タイミングのブレが直接バイアスになる。
- 長期平均方式なら、長期で見れば「買った総量 ÷ 経過時間 ≒ 消費レート」が成り立ち、早買い・まとめ買いのブレが平均化されて相殺される。購入を重ねるほど自己補正的に正確になる。
- 日々の使用記録を求める設計は、正確だが続かない(習慣として破綻しやすい)。記録の負担を「買ったときだけ」に絞ることで継続性を優先し、精度は長期平均と任意補正で担保する。

## 帰結

- 残量は常に推定値であり、ユーザーには「推定」であることが伝わる表示にする。実測が要るユーザーは使い切り/残量補正で原点を直せる。
- 購入が1回だけの品目は仮の値に依存し精度が低い。回を重ねて改善する前提を UI でも示す。
- 消費レート・残量・枯渇予想日・購入推奨日の算出は副作用のない純粋関数(`src/lib/domain`)に置き、単体テストで固定する。
- 「同じ品目でも回によって内容量が異なる」を許すため、レートは内容量固定を仮定せず購入ごとの実内容量を積算する。

## 改訂: 長期平均を recency 加重(指数減衰)にする

当初の「累計 ÷ 経過時間」の等重み長期平均には2つの陳腐化があった。特に使い切いタイアは「最初〜最新の使い切りの全区間」を等重みで平均するため、**大昔の生活パターンが今と同じ重みで永久に混ざり続け**、消費ペースが変わっても反映が遅い(さらに、最新の使い切い以降の購入は次の使い切いを押すまでレートに入らない)。

そこでレート推定を、区間ごとの観測(空→空の各区間、または各購入間隔の「消費量 ÷ 期間」)を **直近ほど重い指数減衰で加重平均**する方式へ一般化した。重みは `wᵢ = 0.5^(何サイクル前か / H)`、半減期 **H = 3 サイクル**。

- **等重み(H = ∞)は従来式に一致**する純粋な一般化で、定常データでは挙動が変わらない(回帰リスクが小さい)。
- 減衰の基準は**日数ではなくサイクル数**。速い品目(2週)も遅い品目(3ヶ月)も「3サイクルで重み半分」と公平になる(日数ベースだと品目速度で不公平)。
- H の値はプロトタイプで筋書き(定常/急増/急減/ノイズ)を比較して決めた。H=3 が「生活変化への追従」と「ノイズ耐性」のトレードオフの膝(現行比でノイズほぼ据え置き・適応は明確に改善)。H は利用者が判断できる概念ではないため UI に露出せず内部定数とする。
- 指数減衰は急には飛びつかず、本物の変化へ数サイクルかけて滑らかに寄る。1回の異常サイクルへの過剰反応を避けるための狙いどおりの性質。
- 使い切り優先(使い切り > 購入 > 仮の値)は維持。減衰は各タイアの中の複数区間の重み付けにのみ効く。

## 再改訂: 使い切りと購入を1つの「品質 × recency」加重プールに統合する

上の減衰版でも、使い切りタイアは使い切り区間だけを見て購入を**丸ごと無視**していた。そのため「使い切いを2回記録したあと、記録をやめて購入だけ溜まる」と、次の使い切りを押すまでレートが古いまま更新されない、という穴が残っていた(消費 outflow は完結した空→空区間でしか正確に測れないという原理的制約に起因する)。

そこで使い切りタイアを、単一プールの加重平均へ統合した:

- **プールの中身** = 使い切り区間(空→空、信頼度 1)＋ **最後の使い切り以降の購入区間**(信頼度 α)。時間的に重複しない(使い切りでカバー済みの期間は使い切りに任せ、購入は「使い切りが届いていない最近の尻尾」だけ足す)。
- **重み = recency 減衰 × 信頼度**。`wᵢ = 0.5^(何区間前/H) · qᵢ`。購入区間の信頼度 **α = 0.5**(使い切いの半分)。購入間隔は「買った分が次までに使い切られた」という定常近似にすぎず、使い切いのような確定サンプルではないため。
- **帰結**: 使い切りをマメに記録している間は tail が生じず**従来どおり使い切り区間だけが支配(回帰なし)**。使い切りが古くなり recency 重みが落ちると、新しい購入区間が相対的に効いてきて、記録をやめても購入ペースへ主導権が移る。tail が使い切りと同ペースなら値は動かない(誤ドリフトしない)。
- α の値はプロトタイプで「使い切りが何サイクル古くなったら購入へ主導権が移るか」を見て決めた。α=0.5 は、fresh な使い切りには一切触れず、別ペースの購入が 2〜3 ヶ月続くと半分ほど寄る中庸。H と同じく内部定数(UI 非露出)。
- なお使い切りが 1 件以下のときは従来どおり購入間隔だけの加重平均に落ちる。

## 再々改訂: 残量を時系列ウォークで求める(レートの遡及適用をやめる)

従来の残量は「アンカー(直近の補正・使い切り・初回購入)残量 + 以降の購入合計 − **現在の**レート × アンカーからの全経過日数」だった。新しい購入でレート推定が変わると、その新レートがアンカー以降の**過去すべての期間に遡って**かかる。まとめ買いをすると「消費が増えた」と推定されて過去分の消費が膨らみ、買い足し分を食い潰す。実データ(トイレットペーパー)でも、8 個買ったのに推定残量は 7.5 → 8.0 しか増えなかった。

そこで残量計算を、イベントを時系列にたどるウォークに変えた(`walkRemaining`)。

- 区間 [tᵢ, tᵢ₊₁] の消費 = **tᵢ 時点で確定している購入・使い切りだけ**から推定したレート × 区間日数。後のイベントは、終わった区間の消費に影響しない。買った分はそのまま残量に乗る(上の例は 7.8 → 15.8)。
- 始点でレートが出せない区間(仮の値なしの初回区間など)だけは、最初に推定できたレートで埋める。消費 0 にすると、補正するまで初回購入分が丸ごと残り続けるため。
- 購入は加算、使い切りは 0、残量補正は実測値へのリセット(誤差のリセット)。
- 残量は 0 で止める(無いものは消費できない)。これに伴い「負の残量で超過を表す」表現は廃止した。枯渇済みの枯渇予想日は 0 に達した時刻で、「◯日超過」は now − 枯渇予想日で出す。残量が正なら now + 残量 ÷ 最新レートで外挿する。
- 表示する消費レートは、従来どおり全データから推定した最新値。
- 履歴グラフ(`remainingTrajectory`)も同じウォークを使うので、グラフの末尾は推定残量と一致する。

あわせて、1 日未満の購入区間(同日の買い足し)はレート推定から除外した。これまで MIN_SPAN_DAYS のガードは全体期間にしか効かず、47 分間隔の購入が「その量を一瞬で消費した」観測としてレートを押し上げていた。

## 改訂: 購入区間の信頼度を区間の長さで割り引く

購入区間は「前回買った分は次の購入までに使い切った」と読んでレートを逆算する。しかし在庫が十分あるうちの買い足し(安売り・配達都合・記録日のズレ)でも区間は短くなり、「速く消費した」という誤った観測になる。実データでは 11/12 0:00 → 11/13 1:16(1.05 日)の買い足しで区間単体のペースが約 7.6 個/日になり、recency 加重で全体のレートが 0.19 → 0.30 個/日に跳ねた。残量は正しく増えても、枯渇予想は「残量 ÷ 最新レート」で外挿するため、あと 41 日 → 53 日にしか伸びなかった。

前回入れた「1 日未満の購入区間は除外」という固定の最小日数ガードでは、1.05 日のように閾値をわずかに超える区間を防げない。閾値を上げても、そのすぐ上の区間で同じことが起きる。また、跳ねたレートは次の購入まで残り続ける。

そこで購入区間の重みに長さの信頼度 `trust = min(1, days / TRUST_FULL_DAYS)`(TRUST_FULL_DAYS = 7)を掛け、`recency 減衰 × quality × trust` とした。

- 1 週間以上の区間はフル信頼で、従来どおり。短いほど線形に割り引くので、閾値の前後で挙動が急に変わらない。上の例ではレート 0.20、あと 78 日になる。
- 購入区間だけのプールにも、使い切りプールの tail にも同じく掛ける。表示レート・ウォークの区間レート・枯渇予想はすべて `consumptionRatePerDay` を通るので、まとめて改善される。
- 使い切り区間(空→空)には掛けない。短期間で本当に使い切ったのなら、それは事実だから。
- 1 日未満の除外ガードは撤廃した(短い区間は trust がほぼ 0 になる)。長さ 0 以下の区間だけ防御的に除外する。
