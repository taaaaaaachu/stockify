# 定期便: アプリ内定義・Amazon 非連携・遅延生成

## 決定

「Amazon定期便」機能は、**Amazon とは一切通信しない**。ユーザーがアプリ内で「この品目を、この間隔で、1回あたりこの内容量×個数、次回◯月◯日」という繰り返し購入スケジュールを定義する、アプリ内で完結する仕組みとする。

定義したスケジュールから実際の購入レコードを生む方式は、**遅延生成**とする。アプリを開いたとき、予定日を過ぎた分の購入を現在まで一括生成する。サーバー常駐の定時ジョブ(cron)は用いない。生成された購入は**自動で確定**し、定期便由来の印を付ける。現実とズレたら個々の購入をスキップ/編集/削除でき、スケジュール自体も編集・一時停止・解約できる。

## 背景・理由

- Amazon には外部アプリが定期便予定を読める公開 API が無い。注文履歴のスクレイピングは規約・2FA・安定性の点で個人アプリに不向き。よって実配送の取り込みは現実的でなく、ユーザー定義スケジュールで代替する。
- 名前は "Amazon定期便" だが実体は「購入を定期的に自動生成する設定」。一定間隔・一定量で届くことは、[消費レート](0001-consumption-estimation-from-purchase-history.md)の強いシグナルにもなる(2ヶ月ごとに1本 ≒ 2ヶ月で1本消費)。
- 遅延生成はゲスト(IndexedDB 完全クライアント完結)でも動き、常駐ジョブという運用要素を持ち込まずに済む。実装も単純。
- 自動確定+事後修正としたのは、「開くたびに1件ずつ承認」では自動登録の意味が薄れるため。アプリ全体の思想(まず自動で推定、ズレは任意で補正)と一致させる。

## 帰結

- 長期間アプリを開かないと自動生成が止まる。ただし次に開いた時点で履歴と推定は現在まで正しく追いつくため、個人利用では許容する。
- Amazon 側でスキップ・数量変更した場合、アプリの生成物が現実とズレうる。個々の購入の編集/削除で手直しできるようにする。加えて、まだ生成していない**次回配送のスキップ**と**次回日変更**をスケジュール側の操作として提供する(未来は次回予定日1点だけなので、どちらも `nextDeliveryAt` を動かすだけで表現できる)。
- 定期便が有効な品目は、自動補充される前提で購入推奨(通知)の対象外とする(この扱いは下記「改訂」で精緻化した)。
- 将来 PWA プッシュ通知を足す段階では、「開かなくても購入推奨日を評価する」ために通知評価用の軽い定時処理が別途要る。定期便の購入生成は遅延生成のまま据え置く。

## 改訂: 購入推奨の除外条件を「次回配送が枯渇前に届くか」で判定する

当初は「アクティブな定期便がある品目は購入推奨を一律除外」としていた。しかし**スキップ**や**次回日変更**で次回配送を先へずらすと、定期便はアクティブなまま次の補充が枯渇より後になり得る。一律除外だと、この状態で静かに在庫を切らしても警告が出ない。

そこで除外条件を、二値の「アクティブか」から「**アクティブな定期便のうち最も早い次回配送日 ≤ 枯渇予想日**(=枯渇する前に補充が届く)」へ精緻化した。

- スキップ/先送りで次回配送が枯渇予想日より後になれば、購入推奨が自動的に復活する。
- 在庫が余っていてスキップした場合は残量が高く枯渇予想日が遠いため、推奨は出ない。両ケースを状態フラグ無し(`nextDeliveryAt` 1点)で自然に捌ける。
- 副作用として、スキップ無しでも「定期便の間隔が消費に追いついていない」品目には推奨が出るようになる。これはむしろ正しい挙動なので受け入れる。

実装は `estimate()` の入力を `hasActiveSubscription: boolean` から「アクティブな定期便の最早次回配送日(無ければ null)」へ変更し、`depletionAt` と比較して購入推奨日を出すかを決める。
