# パスワード検証入口の共通レート制限

## ステータス

採用

## 決定

ブルートフォース対策として、次のパスワード検証入口に共通の認証試行制限を適用する。

- ログイン
- 本人のパスワード変更
- 本人のアカウント削除
- `super_admin`による他ユーザー削除
- 本人確認(再認証)のパスワード経路(ADR 0010 で追加)

同じユーザーに対する失敗回数と、同じIPアドレスからの失敗回数を別々に数える。全入口でカウンターを共有し、入口を切り替えて試行制限を回避できないようにする。パスキーの署名検証(ログイン・本人確認)は総当たりの対象にならないため、この制限の対象外とする。

- ユーザー単位: 15分間に5回失敗すると15分間拒否
- IP単位: 15分間に20回失敗すると15分間拒否
- 成功した認証: 該当ユーザーのユーザー単位カウンターをリセット
- `super_admin`によるパスワードリセット: 対象ユーザー単位のカウンターをリセットし、IP単位のカウンターは維持
- 制限中の応答: 残り回数や解除時刻を表示せず、一般的な認証エラーを返す
- 永久ロック: 採用しない
- CAPTCHA: 今回は採用しない

試行状態はSQLiteに保存する。ユーザー名やIPアドレスそのものは保存せず、用途別のハッシュをキーにする。失敗時刻と制限解除時刻を保持し、24時間より古い状態は認証処理のタイミングで削除する。`X-Forwarded-For`などの転送ヘッダーは、信頼できるプロキシ構成がある場合を除き利用しない。

## 背景・理由

ログインだけを保護すると、パスワード変更やアカウント削除など、同じパスワード検証を行う別のAPIが試行攻撃の抜け道になる。ユーザー単位だけでは複数ユーザーへの分散攻撃を防げず、IP単位だけでは共有回線の正規ユーザーを巻き込むため、両方を一時制限として併用する。SQLiteへの保存はアプリ再起動で制限が消えることを防ぎ、現在の構成に外部サービスを追加しない。

## 帰結

- 認証処理の前後に共通の試行制限サービスを呼び出す必要がある。
- 失敗理由によるユーザー名の存在確認を防ぐため、失敗応答は統一する必要がある。
- テストではユーザー単位、IP単位、入口共有、成功リセット、期限切れ削除を検証する必要がある。
