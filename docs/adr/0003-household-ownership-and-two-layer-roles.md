# 世帯モデルと2層ロール: 在庫は世帯所有、ユーザーは複数世帯に所属

## 決定

会員モードにおいて、在庫データ(ストック品目・購入・定期便・補正・リードタイム既定値など)は個々のユーザーではなく**世帯 (Household)** が所有する。ユーザーと世帯は**多対多**とし、1人のユーザーが複数世帯に所属して UI で世帯を切り替えられる。

ロールは**2層**に分ける:

- **世帯内ロール** (`owner` / `member`): その世帯の在庫とメンバー(招待発行・除名)を管理できるか。世帯ごとに独立。
- **インスタンス管理者** (`super_admin`): サーバー全体の運営者(=開発者本人)。ユーザー管理などインスタンス運営を担う。

招待コードは**特定の世帯へメンバーを招く**もの(既定ロール `member`)。ユーザーが0人のときのみ招待コード不要で初回登録でき、その人がインスタンス管理者になり最初の世帯を作る(ブートストラップ)。

ゲストモードには世帯の概念は無く、単一のローカル在庫として扱う。取り込み時に会員のいずれかの世帯を選んで移す。

## 背景・理由

- 在庫管理は「家族で1つの在庫を共有」が本命の使い方。参照元の lowest_finder はユーザー個人所有(各自の価格比較)だが、この用途にはそのまま合わない。
- 想定する実使用が「1人が複数の家の在庫を管理する」ことであり、1ユーザーが複数の独立した在庫(世帯)を持ち歩く必要がある。単一共有在庫(全会員で1つ)では家ごとに分けられず、ユーザー1世帯固定では両方を1アカウントで見られない。多対多所属が要件に直接対応する。
- ロールを世帯内で閉じるのは、「ある世帯の owner が別の世帯では member」を自然に表すため。一方、サーバー全体の運営(ユーザー削除・ブートストラップ等)は世帯をまたぐので、別レイヤーの `super_admin` が要る。lowest_finder の単一グローバルロールでは、この2つの関心事(世帯運営 vs インスタンス運営)を分離できない。

一般ユーザーも自分で世帯を作成でき、作成者がその世帯のownerになる。世帯ownerまたはインスタンス管理者は、所属するmemberをownerへ昇格できる。

## 帰結

- データモデルが多テナント的になる:在庫系テーブルはすべて `household_id` を持ち、アクセスは所属チェックを通す。
- 世帯切替の状態(現在の世帯)を UI・セッションで保持する必要がある。
- 招待コードに世帯スコープ(どの世帯へ招くか)を持たせる。
- ゲスト → 会員の取り込みは「どの世帯へ入れるか」の選択を伴う。
