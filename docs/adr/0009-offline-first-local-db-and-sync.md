# ADR 0009: オフライン対応(ローカルDB優先 + サーバー同期)

- Status: Accepted
- Date: 2026-10-02

## Context

通信できない場所(店頭・地下など)でも在庫の確認や購入記録をしたい。現状は Service Worker が `offline.html` だけをキャッシュし、アプリ本体(JS/CSS)も会員データもオフラインでは使えない。

推定ロジック(`$lib/domain`)は既にブラウザで計算しており、データ層は `Repository` 抽象でゲスト(IndexedDB)と会員(API)を切り替えている。サーバーの役割を「認証・権限・入力検証・永続化・デバイス間同期・プッシュ通知」に絞り、読み書きはクライアントのローカルDBに対して行う形へ寄せる。

## Decision

段階的に導入する。

### Phase 1: アプリ本体のオフライン起動

- Service Worker は `$service-worker` の `build`/`files` を版ごとのキャッシュへプリキャッシュし、cache-first で返す。
- 画面遷移(navigate)は network-first。成功した同一オリジンの HTML(リダイレクトでないもの)を版ごとのページキャッシュへ保存し、失敗時は同URLのキャッシュ、無ければ `offline.html` を返す。
- `/api/*` はキャッシュしない。
- 旧版のキャッシュは activate で削除する(古い HTML が消えた旧アセットを参照しないため、ページキャッシュも版ごと)。
- ページ HTML にはユーザー名等が埋め込まれるため、ログアウト時にページキャッシュを削除する。
- これでゲストモードは完全にオフラインで動く。会員モードは Phase 2 までオフラインでデータを読めない。

### Phase 2: 会員データのローカル保持(読み取り)

- 会員も IndexedDB をローカルDBとして使う。DB 名は `stockify-<userId>-<householdId>` とし、世帯ごとに分離する。
- サーバーからの取り込み(pull)は既存の `GET /api/state` の全件スナップショットでローカルを置き換える。データ量は世帯の在庫(数百行程度)なので差分同期・tombstone は使わない。
- 読み取りはローカルDBから行う。書き込みは Phase 3 まではサーバー API に送り、成功後に全件 pull する。通信できなければ書き込みは失敗させ、ローカルは変えない。
- サーバーに届かないときは最終同期データで表示し、オフラインである旨のバナーを出す。
- 認証・世帯コンテキストは Phase 1 でキャッシュしたページ HTML に埋め込まれているため、別途保存しない(世帯切替はオンライン限定)。
- ログアウト・アカウント削除時に Service Worker が会員用ローカルDBを削除する。`navigator.storage.persist()` を要求する。

### Phase 3: オフライン書き込み(outbox + 同期)

- 書き込みはローカルDBに反映し、同時に操作(HTTP メソッド・パス・本文・操作日時)を outbox に積む。
- 専用の同期 API は作らず、outbox の操作を既存の `/api/*` へそのまま再送する。既存の入力検証・所有チェックをそのまま通すため。
- ID はクライアントで採番(UUID)して作成 API に `id` として送る。既存データも UUID なのでそのまま混在できる。
- 再送の冪等性は操作ごとの性質で担保する(操作IDの記録テーブルは作らない)。
  - 作成: 同じ ID の行が世帯内にあれば既存行を返す。他世帯の行と ID が衝突したら 404(所有を明かさない)。
  - 更新: 値の上書きなので再送しても同じ結果。
  - 削除: 2回目は 404 になり、クライアントは完了扱いにする。
  - 商品リンクの並べ替え: 操作時の位置 `fromPosition` を添え、サーバーの現在位置と違えば何もしない。
  - これにより複数タブが同じ outbox を同時に送っても重複しない。
- 同期は「サーバーで定期便を遅延生成 → outbox を順に送る(push)→ 全件 pull」の順で行う。outbox が残っている間はローカルを置き換えない(置き換えと outbox の確認は同一トランザクション)。
- 世帯はヘッダー `x-stockify-household` で明示する(Cookie の現在世帯に依存しない)。所属していない世帯なら拒否する。
- **クライアントがサーバーのデータを丸ごと置き換える API は作らない。** サーバーから行が消えるのは、ユーザーが明示した削除操作だけとする。
- 応答の扱い: 2xx と 404 は完了(削除済み対象への操作は破棄 = 削除優先)。401/403 は送信を止めて保持し、再ログインを促す。408/429/5xx と通信不可は送信を止めて後で再送する(順序を守るため後続も送らない)。その他の 4xx(検証エラー・一意制約違反)は破棄してユーザーに通知し、pull でローカルをサーバーに揃える。
- 競合は到着順の後勝ち。
- 定期便の遅延生成で作る購入は `deliveryPurchaseId(subscriptionId, deliveredAt)` で決定的 ID にし、サーバーは重複を無視する。端末もオフライン中に同じ ID で生成するので、複数端末・サーバーで二重生成しない。
- 定期便の「次回予定日は今日以降」の検証は、クライアントがヘッダー `x-stockify-op-at` で添える**操作日時**を基準にする(オフライン中の操作を後から送っても拒否されない)。遡りは最大30日で、未来の日時は現在に丸める。
- 同期契機は起動時・`online`・`visibilitychange`・書き込み直後。Background Sync は iOS 非対応のため使わない。起動時はローカルにデータがあれば同期を待たずに表示する。
- ログアウト時に未送信の操作があれば確認する(ログアウトでローカルDBごと消えるため)。

### 変わらないもの

- 正のデータはサーバーの SQLite。サーバーのスキーマ変更は追加のみ(既存列の削除・型変更をしない)。Phase 3 までで結果的にスキーマ変更・マイグレーションは不要だった。
- プッシュ通知の購入推奨はサーバーのデータで計算する(オフライン中の変更は同期後に反映)。`$lib/domain` はサーバーとクライアントで共有を続ける。
- アカウント・世帯管理・招待・管理者機能はオンライン限定。

## Consequences

- ゲストは Phase 1 でオフライン完結になる。会員は Phase 2 で閲覧、Phase 3 で記録がオフライン可能になる。
- 既存の本番データは移行不要で、削除経路も増えない。
- オフライン中の変更は他端末・通知へ同期まで反映されない。

## Alternatives considered

- ロジックを Service Worker に寄せる: SW はブラウザに任意に停止され状態を持てず、IndexedDB はメインスレッドから使えるため利点がない。
- 差分同期(更新カーソル + tombstone)や CRDT: データ量が小さく全件 pull で足りる。数千行規模になったら再検討する。
- API レスポンスを SW でキャッシュするだけ: 読み取りはできるが書き込みのオフライン化につながらない。
