# ADR 0009: オフライン対応(ローカルDB優先 + サーバー同期)

- Status: Accepted
- Date: 2026-10-02

## Context

通信できない場所(店頭・地下など)でも在庫の確認や購入記録をしたい。現状は Service Worker が `offline.html` だけをキャッシュし、アプリ本体(JS/CSS)も会員データもオフラインでは使えない。

推定ロジック(`$lib/domain`)は既にブラウザで計算しており、データ層は `Repository` 抽象でゲスト(IndexedDB)と会員(API)を切り替えている。サーバーの役割を「認証・権限・入力検証・永続化・デバイス間同期・プッシュ通知」に絞り、読み書きはクライアントのローカルDBに対して行う形へ寄せる。

## Decision

段階的に導入する。

### Phase 1: アプリ本体のオフライン起動

- Service Worker は `$service-worker` の `build`/`files` を版ごとのキャッシュへプリキャッシュし、cache-first で返す。
- 画面遷移(navigate)は network-first。成功した同一オリジンの HTML(リダイレクトでないもの)を版ごとのページキャッシュへ保存し、失敗時は同URLのキャッシュ、無ければ `offline.html` を返す。
- `/api/*` はキャッシュしない。
- 旧版のキャッシュは activate で削除する(古い HTML が消えた旧アセットを参照しないため、ページキャッシュも版ごと)。
- ページ HTML にはユーザー名等が埋め込まれるため、ログアウト時にページキャッシュを削除する。
- これでゲストモードは完全にオフラインで動く。会員モードは Phase 2 までオフラインでデータを読めない。

### Phase 2: 会員データのローカル保持(読み取り)

- 会員も IndexedDB をローカルDBとして使う。DB 名は `stockify-<userId>-<householdId>` とし、世帯ごとに分離する。
- サーバーからの取り込み(pull)は既存の `GET /api/state` の全件スナップショットでローカルを置き換える。データ量は世帯の在庫(数百行程度)なので差分同期・tombstone は使わない。
- 最後に取得した認証・世帯コンテキストをローカルに保存し、オフライン起動時はそれを使う。
- ログアウト時に会員用ローカルDBを削除する。`navigator.storage.persist()` を要求する。

### Phase 3: オフライン書き込み(outbox + 同期)

- 書き込みはローカルDBに反映し、同時に操作(作成・更新・削除)を outbox に積む。
- ID はクライアントで採番(UUID)する。既存データも UUID なのでそのまま混在できる。
- 同期は「outbox を順に送る(push)→ 全件 pull」の順で行う。outbox が残っている間はローカルを置き換えない。
- 同期 API は操作単位で受け付け、各操作は操作ID・世帯IDを明示する(Cookie の現在世帯に依存しない)。サーバーは所属と権限を検査し、入力検証を通し、操作IDで冪等にする。
- **クライアントがサーバーのデータを丸ごと置き換える API は作らない。** サーバーから行が消えるのは、ユーザーが明示した削除操作だけとする。
- 競合は到着順の後勝ち。削除済み対象への操作(404)は成功扱いで破棄し、一意制約違反などは破棄してユーザーに通知する。
- 定期便の遅延生成で作る購入は `subscriptionId + deliveredAt` から決定的 ID を作り、サーバーは重複を無視する(複数端末での二重生成を防ぐ)。
- 認証切れ(401)では outbox を保持し、再ログイン後に再送する。
- 同期契機は起動時・`online`・`visibilitychange`・オンライン時の書き込み直後。Background Sync は iOS 非対応のため使わない。

### 変わらないもの

- 正のデータはサーバーの SQLite。サーバーのスキーマ変更は追加のみ(既存列の削除・型変更をしない)。
- プッシュ通知の購入推奨はサーバーのデータで計算する(オフライン中の変更は同期後に反映)。`$lib/domain` はサーバーとクライアントで共有を続ける。
- アカウント・世帯管理・招待・管理者機能はオンライン限定。

## Consequences

- ゲストは Phase 1 でオフライン完結になる。会員は Phase 2 で閲覧、Phase 3 で記録がオフライン可能になる。
- 既存の本番データは移行不要で、削除経路も増えない。
- オフライン中の変更は他端末・通知へ同期まで反映されない。

## Alternatives considered

- ロジックを Service Worker に寄せる: SW はブラウザに任意に停止され状態を持てず、IndexedDB はメインスレッドから使えるため利点がない。
- 差分同期(更新カーソル + tombstone)や CRDT: データ量が小さく全件 pull で足りる。数千行規模になったら再検討する。
- API レスポンスを SW でキャッシュするだけ: 読み取りはできるが書き込みのオフライン化につながらない。
